# Loomweave interfaces toward Filigree — read-only survey (2026-10-09)

Repo: `/home/john/loomweave`, branch `release/1.6.0` @ `fe8d7a3` (2026-09-02). Nothing was edited, committed, or analyzed. One side effect to disclose: `filigree session-context` in that repo auto-started Filigree's dashboard on `http://localhost:8629` (the same port `loomweave.yaml` names as `integrations.filigree.base_url`; deterministic `8400+sha256%1000`, not a coincidence).

## Executive summary (what matters for Filigree 4.0)

1. **The Loomweave→Filigree and Filigree→Loomweave seams are both proposed for deletion in Loomweave 2.0.** The untracked umbrella plan `docs/superpowers/plans/2026-10-07-loomweave-2.0-remediation.md` recommends **D2: cut all sibling federation incl. "Loomweave's Filigree coupling (emission, `sarif import`, observations, the HTTP read API, HMAC, port publication). Filigree keeps working on its local registry"** (line 108) and **D3: drop SEI, keep the `id` locator** (line 109). These are explicitly **unconfirmed owner decisions** ("confirm or override before Phase 2", §2 line 100-102; §11 line 402-403), the evaluation memo is "non-normative", and all four 2026-10-07 docs are untracked (`git status`). Filigree 4.0 planning is therefore an *input* to the D2/D3 ruling, not downstream of it.
2. **Nothing has shipped from that plan.** Landed-but-unreleased on `release/1.6.0` (post-`v1.6.1`, CHANGELOG `[Unreleased]`): ADR-063 config-trust gate, `.venv` rung trust, bounded git probes. The installed binary is `v1.6.1` (`uv tool list`) and does not carry the trust gate. `main` is at `a454e42` (2026-07-29), 156 commits behind `release/1.6.0`; 1.5.x/1.6.x were never merged to `main`.
3. **Today's wire contract is intact and documented** (`docs/federation/contracts.md`, 1,949 lines), but has **zero live deployments on either direction**: every Filigree config on this host is `registry_backend: local`, aurora has 0 `entity_associations`, Filigree's own "Live Loomweave Integration" and "Federation Sibling Drift" CI lanes have been red since ~2026-08-31 (periphery audit §0.3).
4. **The reliability failure was not the engine; it was silent operational failure twice** (August large-file degradation; 5–24 Sept every analyze failing on the plugin record cap, 42 runs, 0 completed, no alarm). Root cause filed as `clarion-357a7c6f6a` (P1, status `triage`).
5. **Wardline** (which the Filigree 4.0 memory says "owns findings", D1=B2) is recorded by Loomweave's audit as: repo private, 0 `main` commits since 2026-08-26, binary not installed, and the cause of Loomweave's CI being red (a `curl` of a Wardline golden now 404s, `.github/workflows/verify.yml:55-64`). Worth reconciling with the Filigree 4.0 ruling.

### 1a. `docs/implementation/2026-10-07-loomweave-rebuild-or-recover.md` (untracked, 11.7 KB)

**Verdict:** "Do not rebuild. A rewrite would fix the wrong thing." The extraction engine gave correct answers on the one measured real corpus (elspeth, 2026-09-02). Failures are (a) operational reliability on a real corpus, (b) delivery (a separate MCP service agents must choose over `rg`), (c) scope (~1/3 of source serves retired sibling federation). "As of today Loomweave has **no active consumer**."

**Measurements (the reliability bar):**
- elspeth probe lanes on 1.6.1 vs `ast`/`git grep` ground truth: callers 4/4 @100% recall; `inherits_from` 147/147; definition lookup 5/5 rank 1; semantic search 4/5 top-5; median latency 0.09 s, p90 1 s. Still wrong: dead-code, HTTP routes (0/91), `entity_subsystem_get` 74–80 s/call, 4,159 ghost rows.
- Adoption (Claude Code transcripts): 08-29→09-02 ≈0.7–0.8% of lookups; 09-02→09-25 ≈0.18% (66 Loomweave calls vs ~36,300 bash grep/rg) — "not a fair test" because no analyze completed in that window; 09-25→10-07 ≈0%.
- Archived elspeth index: 42 analyze runs 09-05→09-24, **none completed**; 30 failed `plugin python exceeded entity-count cap` (the 500k cap counts entities+edges+findings; Python plugin inflates to ~532k via per-call-site `calls` edges, pre-filter `imports`, `contains` edges); 11 cancelled; each 29–64 min; SEI/incremental state/subsystems written **only on completion**, so every retry was a cold full pass; `imports` edges lost every time.
- Live check on this repo: Loomweave resolved 2/8 callers of `loomweave_core::kill_process_tree` (re-exports reported as `why: dynamic`); `rg` found 8 in 7 ms.
- Scope: 114.6k Rust src lines + 64.7k test; ~21.5k lines suite coupling (federation, HTTP read API, SEI signing/git, guidance, Wardline taint); 48 MCP tools, ~5 observed in use.

**Decisions / recommended path:** (0) choose a consumer first (aurora, Python); (1) reliability precondition before any adoption test: fix the cap (`clarion-357a7c6f6a`), "degrade, don't fail", "report its own health" (run-failure streak in session banner and `doctor`); (2) 2-week push-not-pull experiment: rg-shaped CLI `loomweave callers|defs|subclasses`, edit-time hook, local usage logging, with a **kill date**; (3) only if it passes, carve the lean core: **keep** plugins, storage, ~6 queries, CLI, hook; **delete or feature-gate** "the federation HTTP API, SEI signing/HMAC, guidance, Wardline taint, LLM summaries, worktree indexes and most catalogue tools"; (4) housekeeping: close/re-scope wave 2 (`clarion-983d12c8b8`), PRs #160–#165 unmerged against literal `main`.

**What it says about siblings:** Filigree retired from elspeth in the same commit as Loomweave (2026-09-25, `d479eb2b4`, "not a quality verdict"); aurora kept Filigree, dropped Loomweave only (2026-10-05); Wardline/Legis/Warpline retired from elspeth 2026-08-29.
