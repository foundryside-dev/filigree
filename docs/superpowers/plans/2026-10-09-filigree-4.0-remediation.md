# Filigree 4.0 Remediation and Migration Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> This is a **program plan** across three repos. Phase 0 is written at task granularity and is executable as-is. Phases 1–4 are work packages with fixed interfaces and acceptance tests; each work package gets its own executable plan (via superpowers:writing-plans) when it is reached, because its spec depends on the readings and owner rulings earlier phases produce.

**Goal:** Take Filigree from 3.3.0 to a 4.0 that the owner's agent fleet can trust on real projects: no silent failures, outage detection, a retry-safe core loop, honest "done", and a surface that shrinks to work state — with the Wardline and Loomweave seams rebuilt once, on both sides, instead of deferred.

**Architecture:** Filigree becomes the work-state authority and nothing else (B2): issues, claims keyed to sessions, a six-type lifecycle with a resolution enum and machine-checked completion, and opaque typed *evidence references* instead of a findings warehouse. Producers (Wardline, agents, scripts) push *work candidates* through one promote seam and report evidence state; Filigree never resolves code facts. One registration table generates the MCP catalog, CLI, docs and managed block, and carries an outcome reading and kill-by date per surface item. The HTTP federation surface gets a successor generation with one error envelope; `loom`/`weft` compatibility is a clean break.

**Tech Stack:** Python 3.11+ (uv, ruff, mypy, pytest), SQLite (schema v29 → v30), FastAPI/uvicorn, MCP Python SDK (`mcp>=1.0,<2`), click CLI with `--json`, vanilla-JS dashboard (biome). Wardline: Python 3.12+, stdlib `urllib` client. Loomweave: Rust workspace 1.88, MCP over stdio.

**Spec:** `docs/plans/2026-10-07-refresh-review/` — `00-refresh-brief.md` (owner rulings), `leverage-analysis.md` (its ordering supersedes the brief's §2/§3), the seven lens reports, plus the three documents added 2026-10-09: `review-digest.md` (structured digest of all nine reports, with every finding ID), `loomweave-interface-survey.md`, `wardline-interface-survey.md`. Citations below use the digest's convention (`MCP F3`, `BP-06`, `S-2`, `X3`, `LX-08`, `HTTP F14`, `M-7`).

- Reachability checks always run against the **fetched integration ref** (`git fetch origin && git merge-base --is-ancestor <sha> origin/main`), never local `main` (23 commits behind at the time of writing; the review's "13 valid 3.3.0 anchors read falsely" came from this).
- Actor identity for suite tools in this repo: `claude-filigree`.
- Numbers quoted in this plan use one source per figure: 5,485 logged MCP calls / 15 projects (brief §1); 118 served tools (MCP critique); 9,955 Wardline telemetry rows in this tracker, 8,850 `WLN-L3-LOW-RESOLUTION` (boundaries M-1); `actor` on 61 tools (MCP F10).
- Owner gates (escalate-first, from `vision.md` authority grant + brief §7): deprecating a used feature, deleting or exporting data, doctrine changes, any public release/tag, `ROADMAP.md`/`vision.md` changes. Marked `[OWNER: …]` inline. Nothing below silently assumes a gate's answer.
- No self-deferral of cross-product work: Wardline-side tasks are scheduled in this plan (Phase 3), not listed as "obligations".
- Every new rule ships with its paired measurement (leverage §6): the task that adds a rule names the leading indicator and where it is read.

## Review Focus

Failure modes the spec implies that no task's tests exercise directly. Each line's test is attached to the owning task.

1. **Squash/rebase-merged anchors.** A close cites a branch commit that was squash-merged, so `merge-base --is-ancestor` is false though the work is integrated. Expected: the item waits in `in_review`/`awaiting-integration` with a reason naming the sha and the ref — never a silent pass, never a silent block. → Task 0.6 (warning form), WP-2.3 (gating form): `test_squash_merged_anchor_reports_awaiting_integration_not_pass`.
2. **Cross-repo anchors.** A Filigree issue closed against a Wardline or Loomweave commit (`filigree@…` vs `wardline@…`). Expected: an explicit `repo` qualifier is required for non-local anchors; an unqualified foreign sha is `awaiting-integration`, not "unreachable". → WP-2.3: `test_foreign_repo_anchor_requires_qualifier`.
3. **Two sessions, one actor string.** Two Claude sessions launched from the same `.mcp.json` both present `claude-filigree`; one claims, the other releases/undoes. Expected: claims are keyed to the minted session id; the second session gets `CONFLICT` with `holder_session`, not success. → Task 0.4 (actor-level check), WP-2.1 (session-level): `test_second_session_same_actor_cannot_release_peer_claim`.
4. **`discard` as the new escape lane.** With force-close gone, agents close via `discard(resolution=obsolete)` to avoid evidence. Expected: discard requires a reason, is counted by actor and resolution in the owner digest, and the digest shows the rate. → WP-2.3 + WP-2.8: `test_discard_rate_by_actor_in_digest`.
5. **Fingerprint-scheme bump after promote.** Wardline runs `rekey` (wlfp2 → wlfp3); the next promote for the same defect carries a new fingerprint. Expected: the promote seam either accepts a producer-supplied `supersedes` fingerprint and returns the existing open issue, or creates a new issue and marks the old reference `unknown` — never a silent duplicate with the old reference still `present`. → WP-2.4 + W9: `test_promote_with_supersedes_returns_existing_issue`.
